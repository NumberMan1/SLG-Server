# 服务端架构

## 服务边界

- **Go 运行时**由 Orbit 的 `service.App` 管理网关和登录服的启动与关闭，`socket/http` 提供 HTTP 服务和客户端。Numbox 的 `utils/env` 读取启动配置。
- **Go 网关**是客户端的网络入口。HTTP 登录转发至登录服，TCP 和 WebSocket 共用票据认证。认证后，网关从会话中取账号并将玩法请求转发至游戏服。
- **Go 登录服务**负责管理账号表、校验 MySQL 中的密码哈希，并将 30 秒一次性票据写入 Redis。它通过 etcd 公布内网地址。
- **C++ 游戏服**通过 Orbit v0.4.2 的 `SerialQueue` 运行 `WorldActor`。地图、行军、地块归属和交战状态由同一个权威实例持有。行军抵达、增援入场、战斗推进和战果提交由同一个队列线程顺序处理。一次结算、回合战斗和持续交战都在游戏服内调用 `internal/battle` 的无状态规则。后台写队列把已计算的状态变更追加到 MySQL，另一个后台队列定期生成完整快照。
- **Unity 客户端**负责地图展示、指令提交与行军表现。每 500 毫秒读取带实例标识和同步修订号的世界状态，按单独的地块版本复用地图。客户端用到达时间显示倒计时，游戏服重启后会刷新这一时间。

## 数据与组件

SLG 的数据库选型取决于状态模型和读写路径。这个项目优先选 **MySQL 8.4 / InnoDB**。地块归属、联盟成员、行军状态和结算流水适合用关系表、唯一约束与事务表达。例如，先用唯一的结算 ID 去重，再在同一事务内写入结算流水和领地变更。首个 SQL 迁移创建登录账号表。[数据库目录](../database/README.md) · [MySQL InnoDB 文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html)

MongoDB 适合按单个文档整体读写的聚合，例如结构经常演进的独立战报。它也支持多文档事务，建模时应考虑文档边界与跨文档事务成本。首版战报可先用 MySQL 的 JSON 字段保存详情，再根据查询量和访问模式评估是否引入 MongoDB。[MongoDB 原子性与事务](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)

| 组件 | 用途 | 状态 |
| --- | --- | --- |
| MySQL | 持久化账号和世界状态 | 登录服经 Orbit `storage/mysql` 访问账号表，游戏服经 Connector/C 提交事件与快照 |
| Redis | 短期登录票据、可重建的热点地块缓存和排行榜 | 已接入登录票据，通过 Orbit `storage/redis` 支持 Cluster 和本地单机 |
| Kafka | 战斗结算后的异步事件，例如战报分发和统计 | 存在独立消费者时，与事务 outbox 和消费者去重一起实现 |
| etcd | 多实例服务注册、发现与租约 | 登录服务监听后注册，网关通过 Orbit `discovery.Store` 订阅实例变化 |

网关轮询已发现的登录服务实例，每次登录请求只发送一次。Unity 的玩法消息使用 Protobuf。Go 网关通过长期维护的 Orbit TCP 连接向 C++ 游戏服发送 JSON 载荷，Go 请求层按内网序号匹配响应，网关再用客户端原序号回包。游戏服重连时创建新的请求匹配器，行军重试仍由游戏服按指令 ID 去重。HTTP 只用于对游戏服探活，两条链路连接同一个权威实例。登录服务正常停止时撤销租约，异常退出后 etcd 按租约过期移除实例。Redis 的 `GETDEL` 在槽位主节点上原子消费票据。Cluster 异步复制时，主节点故障切换可能丢失最近的写入，包括消费造成的删除。

## 世界存档与恢复

每个 `SLG_WORLD_ID` 由持有 MySQL 租约的游戏服提供玩法读写和探活。启动先取得租约，再恢复世界。租约有效期为 2 秒，每 500 毫秒续约。`WorldActor` 按时间顺序计算变化，后台写队列在同一事务内推进事件序号、追加变更和回执，并在提交前锁定核验租约。等待事件流或回执行期间，续约仍可继续。游戏服失租后退出，开发容器会自动重启并从存档恢复；其他部署也需由进程管理器监督重启。已有玩家在有效租约内可以继续读取已提交状态。空帧和普通轮询不写事件。

自然补兵根据余额基准和世界时钟计算。查询直接读取推算出的兵力，扣兵和退兵时结算余额。持续只有自然补兵时，每 5 秒最多追加一个世界时钟事件，后续重启从最后一次已提交进度继续。事件生成与提交后发布只更新有改动的地块和交战，完整地图复制留给定期快照。

成功指令按席位版本追加到独立表。席位回收事务提交后，该席位立即退出回执查询范围，后台再分批清理旧记录，重启时只加载现役席位的回执。同一席位可在其他席位回收后确认内容相同的已提交指令。连接中断时沿用原序号、写入者标记和内容重试。若流头仍指向该次提交且内容匹配，则可确认上一次事务已提交。

有未覆盖的事件时，后台按时间间隔或在累计 128 个事件后生成快照。MySQL 在同一事务内对落库的正文计算并登记 SHA-256 校验和。旧快照通过校验后才会替换已有回退点，保存和清理使用独立队列。日志每批最多清理 256 条，删除界限以已通过校验的回退点为准。清理失败会重试，重启后也会继续。最新快照读取或校验失败时，游戏服从上一份快照和保留的日志恢复，再修复最新快照。首次完整读取缺少校验和的旧快照时会补登记。

恢复使用同一 MySQL 一致性视图读取快照，逐行应用后续事件和当前席位的指令记录。事件序号必须连续。游戏服从最后一个事件的纳秒世界时间重建行军和交锋截止时间。停机期间暂停世界，重新开放连接时给已有玩家离线宽限期。已有存档会成为事件流起点，旧版内嵌指令同时迁入独立表。快照失败时记录尚未覆盖的事件数量，便于发现积压。

地图默认半径为 2，可将 `SLG_WORLD_RADIUS` 增大至 7。外围地块按环追加，原地块 ID 和坐标保持稳定。旧存档恢复时先补齐外围，再回放事件。内网和 Unity 原生端及 WebGL 的帧大小已经覆盖半径 7 的完整快照。更大的地图需要区域同步协议。
