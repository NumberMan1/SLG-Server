# 双端协议

## HTTP 注册、登录与会话认证

Unity 向网关发送 `POST /v1/register`，正文为 `application/protobuf` 编码的 `RegisterRequest`。注册时账号和密码均须为 1 至 8 个 Unicode 字符，账号首尾无空白。登录服务将账号和 bcrypt 密码摘要写入 MySQL。创建成功返回 `201` 和空正文，随后客户端可登录获取票据。输入无效返回 `400`，媒体类型错误返回 `415`，账号已存在返回 `409`。设置正数 `SLG_REGISTER_RATE_PER_SECOND` 后，越过每秒限额返回 `429` 和 `Retry-After: 1`。注册并发达到 `SLG_REGISTER_CONCURRENCY` 或登录服务不可用时返回 `503`。

1. Unity 向 Go 网关发送 `POST /v1/login`，正文是 `application/protobuf` 编码的 `LoginRequest`。网关通过 etcd 找到登录服务并转发请求。登录服务查询 MySQL、校验密码哈希，再将有效期 30 秒的票据写入 Redis。网关在 `LoginReply` 中返回票据和自己的 TCP 端口。账号或密码错误返回 `401`，登录服务或存储不可用返回 `503`。
2. Unity 连接登录地址的主机与返回的 TCP 端口，发送 `ConnectRequest`（消息 ID 1），携带票据和协议版本 1。网关用 Redis `GETDEL` 原子地读取账号并消耗票据，然后返回携带账号与会话 ID 的 `ConnectReply`（消息 ID 2）。使用相同 Redis 和票据前缀的网关实例可以共同完成这两步。
3. 客户端收到与请求序号匹配的认证回执后，视为连接成功。票据无效、过期、已使用或协议版本不匹配时，网关关闭连接。当前 TCP 读空闲超时为 15 秒。

Unity Web 使用网页所在站点的 `POST /v1/login`，随后连接同源 `/v1/session` WebSocket。HTTPS 页面选择 WSS。连接请求、回复和 Redis 票据沿用原生客户端的消息定义，WebSocket 每个二进制消息携带一个完整 Orbit 帧。网关将该入口挂载到已有 HTTP 端口，使用 Orbit 的同源校验。

Orbit 帧头为 10 字节大端序，依次是 payload 长度 `uint16`、消息 ID `uint16`、请求序号 `uint32`、保留位 `uint16`。长度不含帧头，保留位为 0，登录联调的单帧 payload 上限为 1024 字节。TCP 是字节流，接收端先读满帧头，再按长度读满正文。

当前默认监听本机明文 HTTP 和 TCP。公网部署时分别为登录入口和 TCP 连接启用 TLS。

## 生成 Go 和 Unity 类型

[proto/session.proto](../proto/session.proto) 和 [proto/world.proto](../proto/world.proto) 定义双端协议。用 `protoc 31.1` 和 `protoc-gen-go v1.36.9` 在服务端仓库根目录执行以下命令。脚本默认将 C# 输出到相邻的 `client` 目录，可通过 `SLG_CLIENT_DIR` 指定其他检出位置。工具路径可用 `PROTOC` 和 `PROTOC_GEN_GO` 覆盖。

```sh
sh scripts/generate-proto.sh
```

## 共享地图与行军

认证后仍使用同一连接。客户端发送 `WorldRequest`（消息 ID 3），网关返回序号相同的 `WorldReply`（消息 ID 4）。只读请求可携带已显示的实例和同步修订号。客户端用同步修订号判断是否与缓存相同。游戏服重启后会更新这个值，客户端会重新收到行军和战斗的到点时间。携带战报游标的客户端通过 `available_troops` 单独读取私有兵力。省略战报游标的旧客户端通过快照读取己方兵力和最近一份战报。

支持地块缓存的客户端总是携带 `known_tile_revision`，首次进入或清除缓存时传 0。回包使用 `tile_revision` 标记当前地块版本。版本匹配时，动态快照可以省略 `tiles`，客户端沿用同一实例和版本的地块。占领、驻军变化或扩图会返回完整地块。省略 `known_tile_revision` 的客户端继续收到完整快照。

认证和玩法请求各自保留 1 KiB 的负载上限。原生 TCP 和 WebSocket 的玩法回包上限为 8 KiB，可承载半径 7 的完整地图。扩图前需同时更新游戏服、网关和 Unity 客户端。

提交行军时携带当前实例、目标格 ID、`command_id` 和出征兵力 `troops`。省略兵力时使用 40。相同指令 ID 的重试须沿用原目标和兵力。游戏服从己方相邻地块选择起点并扣减预备兵力。每名玩家同时可派出一支部队。双方可以向同一块中立地出征，`marches` 中会出现两条目标相同的记录。已有归属的目标在行军和结算期间保留给已受理的进攻。预备兵力初始为 100，低于 100 时每秒补充 5，自动补充最多到 100。撤回的存活部队全数加入预备兵力，可使总数超过 100。出生地受保护。

行军约 3 秒后抵达。游戏服按到达时间处理，到达时间相同则按指令受理顺序处理。先到达中立地块的部队直接占领并驻守，后到的敌军与当时驻军交战。在途部队的 `hostile` 按当前地块归属更新。进攻胜利时存活部队留作驻军。防守获胜时，剩余守军继续驻守，存活的进攻部队返回预备兵力。

试玩地图最多容纳两个账号。连续 60 秒未请求世界后可以回收名额、地块和目标仍然中立的行军。行军目标归敌方时保留双方名额和驻军，待相关战斗全部结算后才回收仍然空闲的名额。战报在名额回收后仍可读取。回收名额时更新世界实例，属于旧实例的指令需要重新选择目标。满员时客户端每隔 5 至 8 秒复查名额。

启用 MySQL 存档时，响应成功的指令和它造成的世界变更已经随事件提交。收到不可用或遇到超时时，客户端沿用原 `command_id`、指令内容和 `known_instance` 重试。其他席位回收后，同一席位仍可确认已提交的原指令，回包可同时带上新实例的快照。旧实例的新指令会返回 `WORLD_CHANGED`。恢复时游戏服加载快照并回放后续事件，行军和交战按最后一次事件的世界时间继续。

## 持续交战与增援

当前 Unity 客户端的进攻指令通过 `continuous_battle` 持续交战。进入敌方地块后，服务端约每秒结算一次双方战损，直至一方兵力耗尽或主动撤出。该模式的 `WorldBattle.continuous` 为真，`round` 表示交锋序号，`round_ends_at_ms` 表示下次交锋的预计结算时间。

双方都可以从相邻领地派一支援军，使用 `reinforce_battle_id` 指定战斗。援军抵达即计入当前战场兵力。游戏服在同一次世界推进内先处理到期行军，再在本进程结算到期交锋。带 `retreat_battle_id` 的撤退指令不派兵，幸存者退回预备兵力。守方撤出时攻方接管地块。战斗结束时仍在路上的援军退回，战报记录实际参战的援军和撤出方。

客户端用 `known_report_id` 按 `report_id` 增量读取最近 8 份战报。该编号按战果提交顺序增长，`battle_id` 仍用于关联实际战斗。旧客户端可继续用 `known_battle_id` 读取，回包按开战编号提供已连续结算的结果。实例变化后从保留的战报重新同步。

## 兼容回合战斗

发起进攻时提交 `round_battle` 会在抵达敌方地块后开始三回合战斗，每回合约 6 秒。首回合开始前冻结抵达的进攻兵力及驻军。前两回合消耗双方兵力，第三回合决定领地归属。`WorldSnapshot.battles` 返回进行中的回合、截止时间、正在作战和已到达待加入的兵力。旧客户端省略两种战斗标记时仍走一次结算。

攻守双方都可以提交带有 `reinforce_battle_id` 的行军指令。每人同时可派一支援军，要求出发地与战场相邻。援军仍需约 3 秒行军，在当前回合结算前抵达才会并入下一回合。决胜回合开始后停止接收增援，赶不到下一回合的援军退回预备兵力。每方在场及待加入的兵力合计最多 300。每回合使用已冻结的兵力快照结算。战报记录回合数和真正参战的援军总数。
